# MindIsle 状态球 App 运行时基线 v0.1

> Status: BASELINE（产品状态、视觉资产契约和验收闭环已冻结）
> Open decision: 最终 App 宿主（Web、原生或跨平台）尚未冻结；宿主只能替换渲染适配器，不得改变产品状态和验收语义。

## 1. 目标与范围

本基线定义中央状态球如何从产品状态变成可运行的 App 视觉组件。它不规定具体框架，也不要求完整 3D 模型。当前目标是让固定正面视角的水球在真实交互中可靠表达 `still`、`transitioning` 和 `moving`。

本基线不包含音乐系统、通知系统、岛屿、商店、社交、自由相机、完整流体模拟和最终移动端性能结论。

## 2. 已冻结的产品事实

产品状态唯一权威：

```text
still → transitioning → moving
reset → still
```

动画、材质、图层和渲染技术都是状态的投影，不得反向定义状态。运动状态是否可以再次触摸回到静止状态仍是独立的人类决策，不在本基线中假定。

状态球是固定正面视觉组件，当前不以自由旋转、完整背面建模或实时物理为目标。视觉完成以参考图、真实输入和状态读取共同证明，不以模型复杂度或渲染技术证明。

## 3. 视觉资产契约

当前静止视觉采用参考驱动的分层资产，包含：

- 稳定层：外壳、内部主体体积、两个内在点位；
- 可动画层：内部明暗边界、内部流层、曲率高光；
- 几何参数：画布尺寸、主体中心、主体半径、点位位置和命中边界；
- 合成顺序：由资产 manifest 定义，不由渲染器自行猜测。

静止资产已达到“可作为运行时输入”的形态，但不等于 App 组件已完成。运动资产还必须补充每层的时间参数、位移范围、透明度变化、裁切规则和过渡策略。

背景应可替换，不能成为状态球组件不可分离的产品语义。水球组件必须能在不改变主体状态和命中区域的情况下替换背景或页面布局。

## 4. 运行时边界

App 运行时需要一个渲染适配器，逻辑上提供以下能力：

```text
loadAssets(manifest)
setState(still | transitioning | moving)
setTransitionProgress(0..1)
setFlowTime(seconds)
setReducedMotion(boolean)
hitTest(point)
inspect()
dispose()
```

渲染适配器必须满足：

- 使用 manifest 的图层顺序和参数；
- 让稳定层和可动画层职责明确；
- 让视觉中心、轮廓和触摸命中区域保持一致；
- 在 `still` 下冻结主要流动和形变；
- 在 `transitioning` 下只改变已约定的视觉参数；
- 在 `moving` 下保持主体中心、主要轮廓和命中区域稳定；
- 能够返回当前状态、视觉就绪、命中区域和渲染诊断信息。

Three.js、原生 Canvas、跨平台 Canvas 或其他技术都可以实现这个适配器。当前任何一种适配器都只是实现，不是产品权威；更换适配器不得改变 manifest、状态契约或验收标准。

## 5. 最小可交付切片

按以下顺序推进，每次只推进一个可观察行为：

### Slice A：静止复现

加载静止图层，在真实运行环境中复现静止合成。验收重点是视觉对比、图层顺序、透明度、主体中心、主体半径和命中区域。

### Slice B：真实点击

使用同一套中心和边界定义完成点击命中。球外点击不改变状态，球内点击产生可读取的事件或状态变化。

### Slice C：过渡

由 `transitionProgress` 驱动内部明暗边界和允许的流层参数，从 `still` 连续进入 `moving`。不加入新的外部装饰。

### Slice D：运动

由 `flowTime` 驱动内部流层和局部高光。运动必须缓慢、连续、可重复，并与静止状态保持同一主体边界。

### Slice E：生命周期

验证挂起、恢复、重置和重复进入。挂起冻结时钟和视觉时间，恢复后只继续一次，不产生跳变或重复计时。

## 6. 简化后的执行流程

MindIsle 借鉴 UniClaw 的证据意识，但不复制其完整治理流程。每个切片只使用以下五步：

```text
确认 → 计划 → 实现 → 验收 → 记录
```

- 确认：确认产品状态、参考图、已有资产和当前真实问题；只在方向有歧义时请求人裁决；
- 计划：只定义一个可观察行为、变更范围和验收条件；
- 实现：只改当前切片，不顺手扩展其他功能；
- 验收：用真实运行、真实输入和状态读取检查结果；
- 记录：留下 `method / expected / actual / evidence` 四元组，并注明未验证事项。

实现缺陷直接回到“实现”；产品语义不清回到“确认”；工具或环境失败只记录为阻塞，不把命令成功当作产品完成。

### Skill 的使用边界

Skill 是按任务启用的辅助工具，不是项目流程的必经阶段：

- 复杂交互或状态化视觉规格：使用交互规格 Skill；
- 需要生成或修改位图参考：使用图像生成 Skill；
- 需要浏览器操作或真实页面验证：使用浏览器 Skill；
- 需要 Blender 建模：只有明确决定采用 Blender 时才使用 image-to-blender Skill；
- 普通代码、静态资产接入和状态验证：不额外引入 Skill。

Skill 不能改变本基线中的产品状态、资产契约或验收标准。

## 7. Astra 前端实践的本地化要求

前端实现应从用户体验开始，而不是从组件或引擎开始：先明确用户看见的状态变化，再让代理提出最小实现。每次视觉修改都要回到真实运行页面比较，而不是只看静态文件。

运行时应提供一个轻量的可观察接口，例如：

```text
window.__MINDISLE__.waterOrb.inspect()
window.__MINDISLE__.session.inspect()
```

至少返回当前状态、过渡进度、流动时钟、视觉就绪、命中区域、计时剩余和挂起状态。接口是测试和调试入口，不是产品 UI。

应提供可重复进入的测试场景或入口：启动静止、进入过渡、运动、重置、挂起和恢复。自动化检查必须使用真实点击和真实状态转移；预先把页面设置成目标截图不能替代真实路径测试。

每次问题处理遵循：

```text
复现 → 截图与状态读取 → 定位 → 最小修改 → 重新运行 → 对比证据
```

截图用于审美和层次，状态读取用于行为和生命周期，性能数据用于设备结论。三者不可互相替代。

## 8. 验收证据

每个切片必须保存：

- 变更范围；
- 预期结果；
- 实际运行方法；
- 实际结果；
- 截图或状态读取证据；
- 未验证事项；
- 下一步或回退条件。

静止视觉通过不等于运动通过；运动通过不等于 App 生命周期通过；浏览器或编辑器通过不等于目标移动设备性能通过。

## 9. 项目文档与长任务记录

文档按职责分层，避免把所有上下文塞进 `AGENTS.md`：

- `AGENTS.md`：稳定的产品目标、状态契约、协作边界和最低验收原则；
- `docs/product/state-ball-visual-spec.md`：水球视觉语言和视觉验收；
- 本文件：当前运行时架构边界、切片顺序和技术验收；
- 实现过程中的状态、决定和未解决问题：记录在对应切片或任务的短状态记录中，不把临时过程写回稳定规则。

每个较长任务只需要维护三个事实：当前切片、完成条件、下一步。验证失败先修复再进入下一切片；不要求为简单修改创建额外的治理文档。

## 10. 决策边界

已冻结：

- 产品状态和状态转移；
- 水球作为固定正面视觉组件；
- 参考驱动的分层资产方向；
- 稳定层 / 可动画层的职责；
- 状态、视觉和验证分离；
- 每个切片的证据闭环。

未冻结：

- 最终 App 宿主技术；
- 渲染适配器的具体实现；
- moving 的具体速度、位移和光泽参数；
- 目标移动设备和最终性能预算；
- 音乐、通知和完整专注流程的产品细节。

任何未冻结事项都不得被历史原型、工具偏好或一次实验结果默默决定。
